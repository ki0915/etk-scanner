## 0. 한 줄 결론

> **설계 철학(정적 탐지 → 저가 분류 → 소수 검증, 비용을 1급 지표로)은 맞다.
> 하지만 구현은 "포트폴리오용 프로토타입" 수준이다.** 탐지 엔진이 이름 휴리스틱이고,
> 정밀도를 측정한 적이 없으며, 비용 수치가 잘못된 단가로 계산되고,
> **LLM이 쓴 PoC를 호스트에서 API 키를 가진 채 실행한다.**
> 바운티에서 성과를 내는 도구가 되려면 탐지 엔진은 검증된 오픈소스에 맡기고,
> LLM은 "판단"과 "실행 검증"에만 쓰는 구조로 재편해야 한다.

### 객관 등급

| 축 | 점수(5점) | 근거 |
|----|:---:|------|
| 설계 방향 | **4** | 계층 캐스케이드, 비용 회계, SARIF, 탐지→수정→실증 사이클 |
| 탐지 엔진 | **1.5** | 함수명 정규식 + 휴리스틱 점수. 데이터 흐름(taint) 없음. JS/TS는 정규식 |
| 검증(PoC) 안전성 | **1** | 호스트 직접 실행, 환경변수 전체 상속, 우회 가능한 import 차단 목록 |
| 정확도 측정 | **1.5** | 재현율만 측정(음성 샘플 없는 데이터셋). 정밀도·오탐률 미측정 |
| 비용 효율(실제) | **2.5** | 아이디어는 좋으나 단가 오류, 캐싱 미작동, 배치 미사용 |
| 엔지니어링 품질 | **2** | 파이프라인 3벌 중복, 단위 테스트 없음, 모델 ID 하드코딩 |
| **종합** | **≈ 2 / 5** | TRL 4(실험실 검증) 수준. 실전 바운티 도구까지는 2~3단계 남음 |

## 1. 잘한 점 (유지할 자산)

공정한 평가를 위해 먼저 적는다. 아래는 v2에서도 그대로 가져간다.

1. **`scripts/pipeline/provider.py` 비용 회계** — 호출별 토큰·비용 기록, 예산 상한 예외,
   배치 API 래퍼까지 갖췄다. 대부분의 오픈소스 LLM 스캐너에는 이 계층이 아예 없다.
2. **"싱크가 아니라 보안 의도를 본다"는 관점** — 권한·검증 우회 같은 로직 버그는 위험 함수가
   없어서 전통 SAST가 놓친다. 보안 판단 함수를 후보로 삼는 발상은 타당하다.
3. **`security_filter.py`의 "공격자가 무엇을 얻는가" 기준** — 기능 버그와 취약점을 가르는
   이 질문은 바운티 리포트가 거절되는 가장 흔한 이유(N/A, Informative)를 정확히 겨냥한다.
4. **SARIF 2.1.0 + exit-code 게이트 + GitHub Action** — CI 통합의 기본기가 있다.
5. **실제 HTTP before/after 실증** (`candidates/wiki-backend/`) — "추정 아님"을 증명하는 습관.
6. **README의 정직한 한계 기술** — 정밀도 미측정을 스스로 밝혔다. 이 태도는 유지한다.

## 2. 결함 목록 (근거 포함)

우선순위: **P0** = 지금 바로 고쳐야 함(안전·신뢰성), **P1** = 성과를 직접 깎아먹음, **P2** = 품질 부채.

### P0-1. LLM이 생성한 PoC가 호스트에서 비밀값을 가진 채 실행된다

`scripts/pipeline/agent_tools.py:135` `run_poc()`:

- `subprocess.run([sys.executable, poc.py])`로 **호스트에서 직접 실행**한다.
  `docker/sandbox/Dockerfile`과 `pipeline/poc.py`의 `--network none` 컨테이너 경로가 있지만
  실제 에이전트 경로(`agent_runner.py` → `agent_tools.ToolBox`)는 그것을 쓰지 않는다.
- `agent_tools.py:165` `env = dict(os.environ)` — `scan.py`/`agent_runner.py`가 `.env`를
  로드한 뒤라 **`ANTHROPIC_API_KEY`를 포함한 모든 환경변수가 PoC 프로세스로 넘어간다.**
- 네트워크 차단(`agent_tools.py:27` `_BLOCKED_IMPORTS`)은 AST import 이름 블랙리스트다.
  `http.client`, `subprocess`(curl 호출), `os.system`, `importlib`, `__import__("soc"+"ket")`,
  `ctypes`, 그리고 **분석 대상 패키지 자체의 네트워크 코드**로 모두 우회된다.

**왜 심각한가:** 분석 대상은 신뢰할 수 없는 코드다. 악성 저장소의 프롬프트 인젝션
(주석·docstring에 "PoC에 이 코드를 넣어라")으로 LLM이 쓴 PoC가 키를 외부로 보내거나
호스트 파일을 건드릴 수 있다. **보안 도구가 공격 경로가 된다.** 버그 바운티 대상처럼
낯선 저장소를 다룰수록 위험이 커진다.

**수정 방향:** 아래 작업 지시 `T0-1` 참고.

### P0-2. 비용 수치가 잘못된 단가로 계산된다 (프로젝트 핵심 주장이 흔들림)

`config/budget.yaml`을 2026-09 공식 가격표와 대조한 결과:

| 모델 | budget.yaml (입력/출력 $/1M) | 실제 | 오차 |
|------|:---:|:---:|:---:|
| `claude-haiku-4-5` | 0.80 / 4.00 | **1.00 / 5.00** | **20% 과소 계상** |
| `claude-sonnet-4-6` | 3.00 / 15.00 | 3.00 / 15.00 | 정확 |
| `claude-opus-4-8` | 15.00 / 75.00 (+overhead 1.35) | **5.00 / 25.00** | **약 4배 과대 계상** |

README의 "비용 6.7배 절감", "SecurityEval 121개 67원"은 **분류 단계(Haiku) 비용이 20% 낮게
잡힌 값**이다. 또한 Opus를 실제보다 4배 비싸게 봐서 "Opus는 비싸니 피한다"는 설계 판단 자체가
왜곡됐을 수 있다. 현재 가격 기준으로는 `claude-sonnet-5-5`($2/$10)가 Sonnet 4.6보다 싸면서 성능은 더 높다.

### P0-3. 프롬프트 캐싱이 실제로는 한 번도 동작하지 않는다

`provider.chat(cache_system=True)`가 system 프롬프트에 `cache_control`을 붙이지만,
**모델별 최소 캐시 길이**에 못 미치면 오류 없이 캐시되지 않는다.

| 단계 | 모델 | system 길이(실측) | 최소 캐시 길이 | 결과 |
|------|------|:---:|:---:|:---:|
| `screen_single.py` | Haiku 4.5 | ~322 토큰 | **4,096** | 캐시 안 됨 |
| `security_filter.py` | Sonnet 4.6 | ~379 토큰 | 1,024 | 캐시 안 됨 |
| `dup_check.py` | Sonnet 4.6 | ~246 토큰 | 1,024 | 캐시 안 됨 |

README의 "prompt caching 지원"은 사실상 동작하지 않는 코드다.
`metrics.json`의 `cache_read_tokens`가 항상 0일 것이다. 직접 확인해 보라.

### P1-1. 탐지 엔진이 "취약점 탐지기"가 아니라 "함수 이름 필터"다

`scripts/pipeline/intent_finder.py`:
- 이름 정규식(`valid|check|is_|has_|parse|token|...`) + 파라미터 이름(`value`, `data`, `s`...)
  + bool 반환 여부로 점수를 매긴다. `is_`, `has_`, `parse`, `strip` 패턴은 거의 모든 코드베이스에서
  수백 개가 걸린다.
- **데이터 흐름(source → sink)을 전혀 보지 않는다.** 외부 입력이 실제로 그 함수에 도달하는지 모른다.
- `scan.py`의 정적 모드는 모든 결과를 `CWE-710`(코딩 표준 위반)으로 내보내고, 점수만으로
  `severity`를 정한다. **CI 게이트가 휴리스틱 점수로 PR을 막는다.** 개발자는 곧 이 게이트를 끈다.
- JS/TS(`intent_finder_multi.py`)는 정규식 기반이라 문법 구조를 모른다.

### P1-2. 정확도를 측정한 적이 없다 (정밀도 = 0개 데이터)

- SecurityEval은 **전부 취약한 샘플**이라 "모두 취약"이라고 답해도 재현율 100%다.
  91.7% 재현율은 정보가 거의 없다(README도 인정).
- **바운티에서 중요한 지표는 정밀도다.** 오탐 리포트는 시간을 낭비하고 플랫폼 신뢰도(Signal)를 깎는다.
- 필요한 것: **취약 버전 / 패치 버전 쌍**이 있는 평가셋. 같은 함수의 패치 전후를 넣어
  "패치 전은 잡고 패치 후는 통과시키는가"를 재야 한다.

### P1-3. 실패를 조용히 삼킨다 → 재현율이 보이지 않게 샌다

- `screen_single.py:104` `if not v: continue` — JSON 파싱에 실패한 후보는 **로그 없이 버려진다.**
- 세 모듈(`screen_single`, `security_filter`, `dup_check`)이 똑같은 수제 JSON 파서를 복사해 쓴다.
- **해결:** Claude API의 structured outputs(`output_config.format`) 또는 `strict: true` 도구 정의를 쓰면
  스키마 준수가 보장된다. 파서 코드 자체가 필요 없어진다.

### P1-4. 비용 레버를 절반만 쓴다

- `provider.batch_submit()`이 구현돼 있지만 **분류 단계는 동기 호출을 쓴다.** 분류는 지연에
  민감하지 않으므로 배치 API를 쓰면 **50% 할인**을 받는다.
- 함수 단위로 코드를 보내지만, 같은 파일의 여러 함수를 보낼 때 파일 컨텍스트를 공유(캐시)하지 않는다.
- `scan.py` 정적 모드에서 diff 기반 증분 스캔이 없다. PR마다 저장소 전체를 다시 훑는다.

## 3. 유사 제품과 비교 — 왜 아직 부족한가

### 3.1 비교 대상

> 라이선스는 2026-10 기준 기억에 의존한 값이다. **코드를 가져오기 전에 반드시 각 저장소의 LICENSE 파일을 직접 확인하라.**

| 제품 / 프로젝트 | 종류 | 핵심 아이디어 | 라이선스(확인 필요) |
|---|---|---|---|
| **Semgrep CE** | 규칙 기반 SAST | 패턴 + taint 모드, 수천 개 커뮤니티 규칙 | 엔진 LGPL-2.1, 레지스트리 규칙은 별도 Rules License |
| **CodeQL** | 쿼리 기반 SAST | 코드를 DB로 바꿔 함수 간 taint 쿼리 | 오픈소스 분석·연구는 무료, 비공개 상용 코드는 GHAS 라이선스 필요 |
| **Bandit** | Python SAST | AST 플러그인 규칙 | Apache-2.0 |
| **OSV-Scanner** | 의존성 취약점 | lockfile → OSV DB 대조 | Apache-2.0 |
| **vulnhuntr** (Protect AI) | LLM SAST | 입력 지점부터 호출 체인을 따라가며 LLM이 필요한 함수 컨텍스트를 요청 | **AGPL-3.0** |
| **IRIS** (연구, ICLR 2025) | LLM + CodeQL | LLM이 source/sink **명세를 추론**하고 CodeQL이 taint 분석 | 저장소 확인 필요 |
| **claude-code-security-review** (Anthropic) | PR diff LLM 리뷰 | diff만 보고 리뷰 + 오탐 필터 단계 | MIT |
| **OSS-Fuzz-gen** (Google) | LLM 퍼징 | LLM이 퍼징 하네스를 생성, 실행으로 검증 | Apache-2.0 |
| **AIxCC 결선 CRS들** (DARPA, 2025) | 자율 탐지·패치 | 퍼징 + 정적 + LLM 앙상블, 패치까지 자동 | 팀별 공개, 개별 확인 |
| **XBOW**, Snyk Code, Copilot Autofix 등 | 상용 | 대규모 검증 인프라 + 사람 검토 | 상용 (참고만) |

### 3.2 정면 비교

| 능력 | ETK-Scanner | 상위권 도구들 | 격차 |
|---|---|---|---|
| 후보 생성 | 함수 이름 휴리스틱 | taint 경로(CodeQL/Semgrep), 호출 체인(vulnhuntr) | **큼** — "도달 가능한 입력"이라는 근거가 없음 |
| 오탐 제거 | LLM 단일턴 판단 | 실행 검증(퍼징 크래시, PoC 재현) + LLM | **큼** — 실행 증거가 있어야 바운티에서 인정받음 |
| 검증 격리 | 호스트 subprocess | 컨테이너/VM, 네트워크·비밀값 분리 | **치명적** (P0-1) |
| 정확도 공개 | 재현율만 | 취약/패치 쌍 벤치마크로 정밀도까지 공개 | **큼** |
| 언어 | Python AST, JS 정규식 | 10개 이상 언어, 실제 파서 | 중간 |
| 비용 회계 | **있음 (강점)** | 대부분 없음 | ETK 우위 |
| 리포트 품질 기준 | "공격자가 무엇을 얻나" 필터 | 유사 | 비슷 |

### 3.3 그래서 "왜 허접한가"를 한 문장으로

> **ETK는 탐지 엔진을 직접 만들려다 이름 휴리스틱에 머물렀고, 그 위에 LLM을 얹었다.**
> 상위권 도구들은 반대로 한다. **탐지는 수년간 다듬어진 결정론 엔진(Semgrep/CodeQL/퍼저)에 맡기고,
> LLM은 그 엔진이 못 하는 두 가지, ① 명세 추론(무엇이 source/sink/검증 함수인가)과
> ② 결과 트리아지·PoC 작성에만 쓴다.** 그리고 모든 주장을 실행으로 검증한다.

ETK의 진짜 차별점은 **비용 회계**다. 탐지 엔진 경쟁은 이기기 어려우니, 검증된 엔진을 가져다 쓰고
"같은 품질을 가장 싸게"라는 축에서 이기는 것이 현실적인 전략이다.

## 4. v2 목표 아키텍처

```
                 ┌─────────────── 무료 (토큰 0) ───────────────┐
 대상 저장소 ──▶ │ ① scope 가드   ② Semgrep / CodeQL / Bandit   │
 (권한 있는      │   (scope.yaml)    + OSV-Scanner(의존성)       │
  대상만)        │                 ③ diff 필터 (PR이면 변경분만)  │
                 └───────────────────────┬─────────────────────┘
                                         │ SARIF 후보 (source→sink 경로 포함)
                 ┌──── 저가: Haiku 4.5, 배치 API(-50%) ────────┐
                 │ ④ 트리아지: 경로 + 슬라이스만 보고 진위 판정   │
                 │   structured output, 저장소 컨텍스트 캐시     │
                 └───────────────────────┬─────────────────────┘
                                         │ 상위 N개
                 ┌──── 고가: Sonnet 5.5 / Opus 5.5 (소수) ──────┐
                 │ ⑤ PoC 작성 → ⑥ 격리 샌드박스에서 실행         │
                 │   (네트워크 없음, 비밀값 없음, 읽기 전용)      │
                 │ ⑦ 패치 후 재실행 → 막혔는지 확인              │
                 └───────────────────────┬─────────────────────┘
                                         ▼
          ⑧ 보안영향 필터 → ⑨ OSV 중복 체크 → ⑩ 리포트 + cost.json
```

핵심 변화 세 가지:
1. **② 탐지를 외부 엔진에 위임.** `intent_finder`는 버리지 않고 "로직 버그 후보" 보조 신호로 강등한다.
2. **④ LLM 입력을 "함수 전체"에서 "taint 경로 + 슬라이스"로 축소.** 토큰이 줄고 판단 근거가 명확해진다.
3. **⑥ 실행 검증을 필수로.** PoC가 실행으로 확인되지 않은 결과는 리포트에 "미검증"으로 표시한다.

## 5. 토큰 효율 레버 (효과 큰 순서)

| # | 레버 | 예상 절감 | 난이도 | 근거 |
|---|------|:---:|:---:|------|
| 1 | **LLM 입력을 taint 경로 + 코드 슬라이스로 축소** (함수 전체·파일 전체 금지) | 입력 40~70% | 중 | 판단에 필요한 줄만 보냄 |
| 2 | **트리아지를 배치 API로** | 해당 단계 50% | 하 | `provider.batch_submit()` 이미 있음 |
| 3 | **캐시가 실제로 걸리게**: 같은 저장소의 공통 컨텍스트(파일 헤더·관련 정의)를 system 앞부분에 모아 최소 길이를 넘기고, `cache_read_input_tokens`로 확인 | 반복 입력 최대 90% | 중 | P0-3 |
| 4 | **PR은 diff 범위만 스캔** | 대부분의 PR에서 90% 이상 | 하 | claude-code-security-review 방식 |
| 5 | **structured outputs로 파싱 실패 0** | 재시도 비용 제거 + 조용한 누락 제거 | 하 | P1-3 |

| 7 | **같은 규칙의 같은 패턴 결과 묶기**: 같은 Semgrep 규칙에 걸린 비슷한 위치는 대표 1개만 판정하고 나머지에 전파 | 후보 수 30~60% | 중 | 중복 판정 제거 |
| 8 | **판정 캐시**: (규칙 ID, 코드 슬라이스 해시) → 판정 결과를 로컬 DB에 저장, 재스캔 시 재사용 | 재스캔 시 대부분 | 중 | 장기 메모리 |

**비용 계측 원칙:** 모든 레버는 `cost.json`에 단계별 before/after를 남긴다. 측정 없이 "절감"이라고 쓰지 않는다.

## 6. "가져다 쓰기" 전략과 라이선스

요청대로 **검증된 프로젝트의 것을 가져와 우리가 수정하는 방식**을 쓰되, 방법을 둘로 나눈다.

### 6.1 원칙: 소스 복사보다 "외부 도구로 호출"이 먼저

| 방식 | 언제 | 라이선스 영향 |
|---|---|---|
| **A. 외부 바이너리/패키지로 호출** (subprocess, pip 의존성) | Semgrep, CodeQL CLI, Bandit, OSV-Scanner | 거의 없음. 각 도구 약관(특히 CodeQL 사용 조건)만 지키면 됨 |
| **B. 아이디어·프롬프트 구조 재구현** | vulnhuntr의 호출 체인 탐색, IRIS의 명세 추론, claude-code-security-review의 오탐 필터 | 없음. 코드를 복사하지 않고 설계만 참고 |
| **C. 소스 복사 후 수정 (vendoring)** | **허용적 라이선스(MIT/Apache-2.0/BSD)일 때만** | 원 저작권·LICENSE 고지 유지, Apache는 NOTICE 유지 |

### 6.2 프로젝트별 권장

| 대상 | 권장 방식 | 이유 |
|---|---|---|
| Semgrep CE + 커뮤니티 규칙 | **A** | 규칙을 저장소에 복사하지 말고 실행 시 레지스트리/로컬 규칙팩 참조 |
| CodeQL | **A** | 본인 오픈소스·공개 저장소 분석에 적합. 비공개 상용 코드는 라이선스 확인 |
| Bandit, OSV-Scanner | **A** | 그대로 의존성으로 |
| **vulnhuntr** | **B (복사 금지)** | AGPL-3.0. MIT 저장소에 복사하면 전체가 AGPL 의무를 짐. 빈 `vulnhuntr/` 폴더는 삭제 |
| IRIS | **B** | 핵심은 "LLM이 source/sink 명세를 만들고 CodeQL이 경로를 찾는다"는 설계 |
| claude-code-security-review | **C 가능** (MIT 확인 후) | 오탐 필터 프롬프트와 diff 처리 로직을 참고·이식 |
| OSS-Fuzz-gen | **B / A** | Python은 Atheris, JS는 jsfuzz 계열로 하네스 생성 아이디어만 차용 |

### 6.3 도입 시 체크리스트 (매번)

- [ ] 저장소 LICENSE 파일을 직접 열어 확인
- [ ] `THIRD_PARTY_NOTICES.md`에 이름·버전·라이선스·출처 URL 기록
- [ ] 복사한 경우 원본 커밋 해시를 파일 상단 주석에 기록
- [ ] AGPL/GPL 코드는 복사하지 않음 (외부 프로세스 호출만)

## 7. ADHD 친화 학습·보상 설계

> 이 장은 의학적 조언이 아니라 **작업 구조 설계**다. 목표는 세 가지다.
> 1. 시작이 쉬울 것
> 2. 끝났다는 신호가 즉시 올 것
> 3. 쌓인 것이 눈에 보일 것

### 7.1 설계 원칙

| 원칙 | 이 프로젝트에서의 구현 |
|---|---|
| 다음 할 일은 하나만 보여준다 | `python scripts/quest.py` 를 치면 지금 할 퀘스트 1개만 나온다 |
| 작업 단위는 25분 안팎 | 모든 퀘스트를 25분 블록 1~3개로 쪼갰다 |
| 끝은 기계가 판정한다 | 퀘스트마다 검증 명령이 있다. PASS가 떠야 완료 |
| 보상은 즉시, 눈에 보이게 | 완료 순간 XP와 레벨 진행 바를 출력한다 |
| 실패해도 잃는 것이 없다 | 연속 기록(streak) 없음. 누적 XP만 늘어난다 |
| 멈춘 지점을 기억해 준다 | `quest.py note "..."` 로 메모, 다음 실행 때 맨 위에 다시 보여준다 |
| 지루함을 막는 변화 | 퀘스트 유형을 섞는다: 만들기 / 부수기(검증) / 배우기 / 리뷰 |

### 7.2 퀘스트 유형 4가지

| 유형 | 아이콘 | 하는 일 | 보상 포인트 |
|---|:---:|---|---|
| 만들기 (Build) | 🔨 | 기능 하나를 구현 | 테스트 PASS |
| 부수기 (Break) | 🗡️ | 내가 만든 것을 공격해 본다. 샌드박스 탈출 시도, 오탐 유도 등 | 공격이 막히면 PASS |
| 배우기 (Learn) | 📚 | 과거 공개 CVE 하나를 샌드박스에서 재현하고 3줄 요약 | 재현 성공 |
| 리뷰 (Review) | 🔍 | Devil's Advocate 체크리스트로 발견 하나를 반박해 본다 | 체크리스트 완료 |

**보스전:** 각 Phase 마지막 퀘스트는 "실제 결과물" 하나다.
예: 평가셋에서 정밀도 숫자를 처음 얻는 것, 오픈소스에서 실제 버그 하나를 확인하는 것.

### 7.3 레벨

| 레벨 | 누적 XP | 칭호 | 할 수 있게 되는 것 |
|:---:|:---:|---|---|
| 1 | 0 | 견습 | 도구를 안전하게 돌린다 |
| 2 | 100 | 측정가 | 내 도구의 정밀도·재현율을 숫자로 말한다 |
| 3 | 250 | 사냥꾼 | Semgrep/CodeQL 후보를 LLM으로 트리아지한다 |
| 4 | 450 | 증명가 | 샌드박스에서 PoC로 before/after를 증명한다 |
| 5 | 700 | 리포터 | 받아들여지는 품질의 리포트를 쓴다 |

### 7.4 리뷰·검증 체크리스트 (모든 발견에 적용)

발견 하나당 아래를 순서대로 체크한다. 하나라도 "아니오"면 리포트하지 않는다.

1. **도달성**: 외부 입력이 이 코드까지 실제로 도달하는 경로를 파일:줄로 적을 수 있는가?
2. **실행 증거**: 샌드박스에서 PoC가 실제로 동작했는가? (추정 금지)
3. **공격자 이득**: 공격자가 구체적으로 무엇을 얻는가? (접근, 데이터, 실행, 우회, DoS)
4. **반박 시도**: "이건 의도된 동작이다", "문서에 지원 안 한다고 쓰여 있다", "전제 조건이 비현실적이다" 세 가지 반론을 직접 써 보고 각각 반박했는가?
5. **중복**: OSV/GHSA와 저장소 이슈·보안 탭을 검색했는가?
6. **범위**: 대상이 내 소유이거나, 오픈소스이거나, 바운티 scope 안에 있는가?
7. **패치 검증**: 수정안을 적용하면 같은 PoC가 막히는가?

## 9. 범위(scope) 가드 — 기능이자 원칙

버그 바운티에서 scope 밖 테스트는 리포트 거절과 계정 제재의 주된 이유다.
그래서 범위 확인을 사람의 기억에 맡기지 않고 **도구가 강제**한다.

```yaml
# scope.yaml (예시)
owner_assets:            # 내 소유 — 정적·동적 모두 허용
  - repo: github.com/ki0915/*
open_source:             # 소스 분석 + 로컬 샌드박스 재현만, 실서비스 접속 없음
  - pypi: datasette
bounty_programs:         # 프로그램 정책의 in-scope 목록을 그대로 옮김
  - name: example-program
    in_scope: ["api.example.com"]
    rate_limit_rps: 2
```

규칙:
1. 분석 시작 전에 대상이 `scope.yaml`에 있는지 확인하고, 없으면 중단한다.
2. 동적 검증은 기본적으로 **로컬 복제 환경**(docker-compose)에서만 한다. 실서비스 대상 요청은 바운티 in-scope 항목에 한해, 정책의 요청 속도 제한을 지킨다.
3. 오픈소스 발견은 공개 이슈가 아니라 관리자의 보안 정책(SECURITY.md, GHSA 비공개 보고)으로 보낸다.
